# Review pass: error handling (whole repo)

Scope: `src/main` + `src/test`, every `catch` block, every exit-code branch, and the state-recording paths.
Deliberate degradations listed in the brief (git unavailable, best-effort live schema read, best-effort
version check, broken cycles, `XmlPretty` fail-safe, user-declined = exit 0, per-object rejection continues)
were checked for *reporting*, not reported as findings in themselves.

## Findings

major | src/main/java/de/is4it/midpoint/diff/RemovalDetector.java:306 | An unrecoverable last-applied revision is indistinguishable from "nothing was removed": `git show <rev>:<path>` returns null on a rewritten/squashed history (or a 15 s git timeout), every fragment is treated as "new file since the last deploy", `deploy` prints no removals, and — because it still exits 0 — `recordRevision` advances the baseline, so those removals can never be detected again. | Verify the recorded revision once per run (`git rev-parse --verify <rev>^{commit}` / `cat-file -e`); if it does not resolve, say so loudly, refuse `--prune`, and do not advance the recorded revision.

major | src/main/java/de/is4it/midpoint/diff/RemovalDetector.java:256 | `declarationsByObject` swallows any failure of the "what does this fragment declare" diff at DEBUG (same for the `emptyLike == null` `continue` at :243) and still leaves the object's key in the map, so the survivor set is silently empty — values a sibling fragment still declares then pass the `stillDeclares` subtraction as removals and `--prune` deletes, right after the apply pass wrote them. | Propagate the failure (or mark that object as "declarations incomplete") and exclude it from removal detection/prune instead of continuing with a partial survivor set.

major | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:280 | The revision is recorded whenever the run exits 0, but `declined` is only set by the whole-tree prompt: a run where units were `SKIP`ped (OID-less fragment without `--create-if-absent`/`--match-by-name` — reachable non-interactively with `--yes`) or declined per unit under `--confirm-each-apply` records the tree as fully deployed although those values were never applied. | Record only when the pass actually applied or confirmed every unit — track skipped/declined units in `Tally` and gate `recordRevision` on `skipped == 0 && !declined`.

major | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:900 | Declining the prune prompt returns 0 and then records the new revision (see the comment at :274), which destroys the very information the prune needed: the next `deploy --prune` compares against the new revision, finds nothing, and the values the operator wanted to review first stay on the server for ever. | On `ABORTED` in `confirmPrune`, keep the exit code 0 but suppress `recordRevision` (or record only after the removals are resolved), so the pending removal set survives to the next run.

major | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:341 | A failure to read `midgie-state` (e.g. the deploy account has no read on `lookupTables` → HTTP 403, or the `?include=row` GET fails) is logged at DEBUG only and silently disables both removal detection and revision recording — unlike the three neighbouring "cannot detect" branches, which all `note(...)`. The operator who just ran `midgie init` gets no hint that tracking is dead. | Emit the same `note("note: removals cannot be detected — could not read midgie-state: …")` here, with the exception message.

major | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:532 | A file that Discovery classified as a candidate object but prism cannot parse (a typo'd item, an extension whose schema failed to load — cf. Discovery.java:102) is dropped with a warning and `deploy` exits 0; under `--quiet` `emitWarnings` prints nothing at all, so `deploy --url … --yes --quiet` reports total success while a role/system-configuration fragment was never deployed. Verified: `deploy tree` with one unparseable role prints the warning and exits 0. | Count parse failures as failed units (exit 2), or at minimum print them on the "errors only" channel that `--quiet` keeps, so CI cannot go green on an undeployed object.

major | src/main/java/de/is4it/midpoint/diff/MidpointRestClient.java:241 | `retryable` is `"GET".equals(method)`, but every object lookup in `diff --url`/`apply`/`deploy` goes through `POST {type}/search` (LiveLookup.search), so `--retries` never applies to them: with `--no-live-schema` (or after a mid-run restart) the first 503/connection-refused from a starting midPoint aborts the whole run despite `--retries 30`, which is exactly the "rides out a server that is still starting" case DESIGN.md promises. | Mark the search endpoint retryable explicitly (e.g. an `idempotent` flag on `sendRaw`, set by `searchObjects`/`listObjects`/`getObject`), keeping true writes non-retryable.

major | src/test/java/de/is4it/midpoint/diff/RemovalDetectorTest.java:49 | Every git-backed test bails with a bare `return` when `commit()` fails (`:49, :66, :82, :111, :140`; same pattern in GitRevisionTest.java:66, :90, :133), so on a machine or build image without git — or where `git commit` is refused by a global hook/signing policy — the whole prune-safety suite reports **passed**, not skipped, and a regression in the logic that deletes live config ships on a green build. | Use `Assumptions.assumeTrue(first != null, "git unavailable")` (the convention LiveIntegrationTest already follows) so the environment failure shows up as a skip.

minor | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:800 | `--apply-plan --confirm-each-apply`: entries the operator declines are neither applied nor added to `failed`, yet the summary computes applied as `entries.size() - failed.size()`, so declining 3 of 5 prints "Done: 5 applied, 0 failed" — contradicting the per-entry `skipped declined` lines. | Count declined entries separately and report "N applied, M skipped, K failed".

minor | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:414 | A removal with no item definition is reported through `note(...)` — suppressed by `--quiet` — is not counted in `failed`, so `deploy --prune --quiet` exits 0 having removed nothing for that value, and the subsequent `recordRevision` drops it from the removal set permanently. | Count it as a prune failure (so the exit code and the revision gate see it), and print it on the channel `--quiet` keeps.

minor | src/main/java/de/is4it/midpoint/diff/DeployCommand.java:393 | `--plan --prune` (and `--apply-plan --prune`) are accepted but prune never runs there (`planDir == null` guard at :266, early return at :194), while `reportRemovals` still prints "(--prune: removing)" — the operator reviews the plan, replays it, and the values are silently still on the server. | Either reject `--prune` together with `--plan`/`--apply-plan`, or word the line as "(--prune: not applied in plan mode)".

minor | src/main/java/de/is4it/midpoint/diff/ApplyCommand.java:166 | After a create whose response carries no `Location` header (e.g. behind a proxy that strips it) on a `--match-by-name` target, `target.oid` is also null, so the success line reads `Created roles/null.` — a bare value that tells the operator nothing about what was created. | Fall back to the object's name (`LiveLookup.nameOf(desired)`) and say the OID was not reported by the server.
